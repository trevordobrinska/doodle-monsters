# 01: A kid's whole Zoo emptied without Say Goodbye

> *This was generated by AI during triage.*

**Category:** bug
**Status:** ready-for-human
**Related:** `.scratch/doodle-monsters-v1/issues/13-run-night-1.md` (the "saved data survives" check), `.scratch/doodle-monsters-v1/issues/14-finalize-storage-backup-restore.md` (storage hardening, server backup follow-up)

## Report (2026-11-09)

All of my son's Monsters disappeared from his Zoo after he'd caught 6 or so. He didn't Say Goodbye to any of them. He was catching one Monster after another, and then they were gone. There was no reboot, update or break in between. He always opens the game the same way, from the Arcade in My Stuff. The Zoo is still empty.

## Triage findings

**The game's code isn't deleting Monsters.**
- Only Say Goodbye removes a saved Monster. The dev-only placeholder switch can remove one too, but it never ships in the build.
- Saving writes one Monster record at a time and never clears the store.
- No other game on the shared `trevordobrinska.github.io` origin touches the `doodle-monsters` database. The Arcade, the Night 1 page and the Secret Script Studio tablet test each delete only their own data.

**The browser's storage for the whole origin was cleared.**
- On 2026-11-08, Night 1 card 2 saved visits in this profile.
- On 2026-11-09, the same card reads "Last save: nothing yet", so the `night1-test` database is gone too. That database has nothing to do with the game.
- So storage for the whole origin was wiped or lost, not just the game's records.
- Night 1 had already recorded **Persistent storage: Not granted** on both tablets. The "survives a reboot and a few days" check in ticket 13 was never finished.

**A reload made the loss visible.**
- Once loaded, the Zoo lives in memory, so it can't vanish on screen without a page load.
- So the page reloaded mid-session and found empty storage. Possible reloads: going to the Arcade and back, or the 2 GB tablet discarding the page in the background.
- What actually cleared the storage isn't known. Candidates: the Kids profile's web view keeping site data only until its process ends, or the browser evicting best-effort storage.

**Not tested:** the "Zoo failed to load and opened empty" path. It can't explain the empty Night 1 card, but it still fails silently: the error goes only to the console and the Zoo opens empty.

## Why this needs a human

- The real fix is a design decision. On-device storage in a Kids profile can't be relied on, and `persist()` is refused. The safety net is the server backup that ticket 14 already flagged for V1.5 (Night 1 card 7 shows a Kids profile can reach an outside HTTPS server). Choosing to build it now, and how, is the builder's call.
- Narrowing the cause takes the tablet. Each check below shows which kind of clearing it is.

## Next checks on the tablet (builder)

- [ ] In his profile, open the Night 1 page so card 2 records a visit. Then close the browser or Arcade fully (swipe it away from recent apps) and reopen the Night 1 page. Is the visit still there?
- [ ] Same again, but go to the Arcade and back instead of closing.
- [ ] Same again after a reboot.
- [ ] Check the tablet's free storage (Settings → Storage).
- [ ] Optional: check the other kid's profile on the other tablet the same way.

If closing the app wipes it, storage only lasts as long as the process. Nothing on the device will keep a Zoo, so server backup becomes a must for V1.

## Possible follow-ups once the cause is known (agent-ready later, not yet filed)

- Ask for persistent storage at startup and record the answer (ticket 14 already covers this).
- When the Zoo can't load, don't silently show an empty Zoo. Show something a grown-up can notice, and don't let new saves pretend all is well.
- Server backup of the Zoo (V1.5 per ticket 14). It needs a spec first.

## Comments

**2026-11-09, later (builder, recorded by agent):** > *This was generated by AI during triage.* The tablet checks all passed, and the visits stayed in card 2 through each one:

- [x] closing the app fully and reopening
- [x] going to the Arcade and back
- [x] rebooting
- [x] free storage: 1.6 GB

So the storage keeps data in normal use, and the wipe was a one-off. We can't make it happen again on demand. What's left, most likely first:

1. **The browser evicted the site's best-effort storage** because the tablet ran low on space. Free space is 1.6 GB now, but it may have dipped further at the time, for example during an app update or a video download. `persist()` is refused, so the site isn't protected from eviction.
2. **Fire OS or Amazon Kids cleared web data**, for example a Kids app update or a Parent Dashboard change.
3. **Caveat:** this assumes the earlier "nothing yet" Night 1 check was opened the same way as the game, from the Arcade in My Stuff. If it was opened in the Kids web browser instead, that storage may be separate, and the "whole site was cleared" finding is weaker. The Zoo itself was definitely lost in the Arcade.

Causes 1 and 2 are both outside the game's control, so the fix stays the same: a copy of the Zoo off the device (server backup).

**Proposed agent-ready follow-up: catch it next time.** After each successful save, the game keeps a small note in a second store (localStorage): the Zoo's Monster count and the time. On load, if IndexedDB comes back empty but the note says there were Monsters, it records "Zoo found empty, expected N, last seen at T" where a grown-up can see it. If the localStorage note survives a wipe, it also shows which kind of wipe it was.
